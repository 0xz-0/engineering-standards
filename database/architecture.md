# 数据库架构红线规范

> **约束力**：MUST
> **适用范围**：所有业务关系型数据库（PostgreSQL / MySQL 等）
> **核心哲学**：数据库仅作为"高性能存储与索引引擎"，所有业务逻辑、数据一致性校验由应用层负责。

## 1. 背景与目的

高并发 OLTP 场景下，数据库的每一次行锁、每一次约束检查、每一个触发器，都是横向扩展的阻力。本规范明确**应用层与数据库层的责任边界**：

- **数据库负责**：存储、索引、查询、事务（ACID）；
- **应用层负责**：业务逻辑、数据一致性校验、关联完整性维护、审计字段维护。

## 2. 禁用清单（明确红线）

以下数据库对象/特性在所有业务库中被**全面禁止**：

| 禁用项 | 理由 |
| :--- | :--- |
| ❌ 物理外键（`FOREIGN KEY`） | 写入时级联检查产生行锁，高并发下成为瓶颈；分库分表、数据迁移时成为障碍。关联完整性由应用层保证 |
| ❌ 检查约束（`CHECK`） | 业务校验规则变更需 DDL，且报错信息对应用层不友好。校验前置到应用层 |
| ❌ 存储过程（`PROCEDURE`） | 业务逻辑下沉到数据库，无法随应用发版、无法单元测试、难以排查 |
| ❌ 函数（`FUNCTION`）及触发器函数 | 同上 |
| ❌ 触发器（`TRIGGER`） | 隐式副作用难以追踪，问题排查困难。**因此 `updated_at` 必须由应用层维护** |
| ❌ 视图（`VIEW`） | 隐藏真实查询复杂度，性能黑盒；只读报表需求需另行审批 |
| ❌ `UUID` 作为主键 | 无序导致索引页分裂、体积是 bigint 的 2 倍、不利于范围扫描 |
| ❌ 数字枚举入库 | 状态值存 1/2/3 依赖各端枚举定义顺序严格一致，任何一端插入/调整都会静默错位。统一用 `TEXT` 语义化字符串 |

## 3. 逻辑外键约定

虽禁止物理外键约束，但**逻辑外键关系必须显式表达**：

- 关联字段命名遵循 `[被引用表名单数]_id`（详见[命名规范](naming.md)）；
- 逻辑外键必须被索引覆盖（详见[索引规范](indexing.md)）；
- 字段注释必须标注 `关联 [表名.字段名]`（详见[表设计规范](table-design.md)）。

## 4. 多业务域隔离

不额外划分业务 schema / 数据库（高并发 OLTP 场景下增加路由与运维复杂度，收益有限）。多业务域隔离通过**表名前缀**实现，如 `pay_order_info`、`msg_notification`。

## 5. 例外审批

以下场景可申请豁免，需在表注释或迁移脚本中说明理由：

- 只读报表库的视图；
- 数据订正脚本中的一次性函数；
- 与遗留系统对接的过渡方案（必须标注下线计划）。
