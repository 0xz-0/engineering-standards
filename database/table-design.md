# 数据库表设计规范

> **约束力**：MUST
> **适用范围**：所有业务关系型数据库（PostgreSQL / MySQL 等）
> **说明**：本文约定跨数据库通用的表设计原则；字段类型的具体选型（如 `timestamptz` vs `datetime`）见各数据库专项规范。

## 1. 主键策略

- **强制自增大整数**（64 位）：各数据库的落地语法见专项规范（PostgreSQL 用 `bigint` + IDENTITY，MySQL 用 `bigint` + `AUTO_INCREMENT`）；
- **严禁 `UUID` 作主键**：无序导致索引页分裂、体积翻倍、不利于范围扫描；
- **严禁业务字段作主键**：主键必须不可变、无业务含义。

## 2. 金额字段

- **强制 64 位整数**，命名以 `_cents` 结尾（单位：分）；
- **严禁 32 位 int**（上限约 21.47 亿分 ≈ 2147 万元，订单总额、余额、累计统计必然溢出）；
- **严禁浮点**（`float` / `double` 精度问题，财务场景不可接受）。

## 3. 时间字段

- 存储内容统一为 **UTC 时间**，时区转换在应用层/展示层完成；
- 具体类型选型见各数据库专项规范。

## 4. 枚举/字典值存储约定（强制）

`_status` / `_type` 字段**强制使用字符串存储语义化枚举值**，值采用全大写 `SCREAMING_SNAKE_CASE`（如 `INIT`、`PENDING_PAYMENT`、`PAID`、`SHIPPED`、`COMPLETED`、`CANCELED`）。理由：

1. **数据库自文档化**：直接查库即可读懂业务状态，无需对照代码枚举表反查数字含义（排障、数据订正、BI 取数场景收益最大）；
2. **跨语言/跨系统零歧义**：字符串值自带语义，不依赖某一端代码的枚举定义；
3. **杜绝数字枚举错位事故**：数字枚举依赖各端定义顺序严格一致，任何一端插入/调整枚举值都会静默错位。

**严禁使用数字枚举入库**（存 1/2/3）。应用层（如 Go）内部可以使用 `iota` 等数字枚举提升效率，但**落库前必须映射为语义化字符串**；查询 SQL、数据库注释、数据导出中一律不得出现裸数字状态值。

**枚举值变更纪律**：枚举值本质是对外契约，**只允许新增、不允许改名/删除**；废弃值保留并在注释中标注 `(废弃)`，防止历史数据无法解读。

## 5. 必备审计字段（分层强制）

| 字段名 | 约束 | 适用场景 | 必要性 |
| :--- | :--- | :--- | :--- |
| `created_at` | `NOT NULL`，默认当前时间 | **所有表**（含主表、关联表、日志表、字典表） | **MUST**（唯一豁免：纯缓存映射表，需在表注释中声明） |
| `updated_at` | `NOT NULL`，默认当前时间 | 需要记录数据变更的业务主表 | **SHOULD**（按场景决策卡执行） |
| `deleted_at` | `DEFAULT NULL` | 需要"软删除"逻辑的业务主表 | **MAY**（按场景决策卡执行） |
| `version` | `NOT NULL DEFAULT 0` | 存在高并发更新冲突风险的表（库存、余额） | **MAY**（按场景决策卡执行） |

**`updated_at` 维护责任（MUST）**：因触发器被禁用（见[架构红线规范](architecture.md)），`updated_at` **由应用层负责**在每次 `UPDATE` 时显式赋值（或通过 ORM 钩子自动更新）。数据库默认值仅兜底首次插入，不保证后续更新。

**场景决策卡**：

| 表类型 | 推荐包含字段 | 说明 |
| :--- | :--- | :--- |
| 核心业务主表（用户、订单、商品） | `created_at` + `updated_at` + `deleted_at` + `version` | 全量包含 |
| 纯关联关系表（硬删除） | `created_at` | 仅记录建立时间，物理删除 |
| 操作日志 / 审计日志（Append-Only） | `created_at` | 仅追加，永不修改 |
| 高频扣减表（库存、余额） | `created_at` + `updated_at` + `version` | 必须加乐观锁，通常不做软删除 |
| 静态字典表（`config`、`dict`） | `created_at` + `updated_at` | 配置变更需记录更新时间 |

**`deleted_at` 与 `_status` 的语义边界（MUST）**：`deleted_at` **仅表示记录级删除**（数据对用户不可见、不进查询结果）；业务状态流转（含"已取消"、"已关闭"等终态）**一律走 `_status` 字段**。两者正交，严禁用 `deleted_at` 表达业务状态，也严禁用 `_status` 表达记录删除——否则同一实体会出现 `status=已取消但 deleted_at 为 NULL` 与 `deleted_at 非空但 status=进行中` 两种分裂写法，部分唯一索引（见[索引规范](indexing.md)）的语义也会被破坏。

## 6. 注释规范（强制）

**核心原则：数据库必须"自文档化"。** 任何脱离代码能看懂的注释，都是有效的注释。具体语法见各数据库专项规范（PostgreSQL 用 `COMMENT ON`，MySQL 用 `COMMENT '...'`）。

### 6.1 表注释（强制）

- **格式**：`[业务含义]；[数据来源/用途说明]`
- **示例**：`订单主表，存储用户下单的核心订单数据。`、`用户与角色的关联关系表（纯关联，硬删除）。`

### 6.2 字段注释的四种强制场景

| 场景分类 | 注释模板 | 示例 |
| :--- | :--- | :--- |
| **普通业务字段** | `[业务含义]` | `订单编号，用户侧展示的唯一业务编号。` |
| **逻辑外键关联字段** | `关联 [表名.字段名]；[业务含义]` | `关联 user_info.id；下单用户ID。` |
| **冗余字段** | **`[冗余] 来源：[表名.字段名]；[业务含义/缓存目的]`** | `[冗余] 来源：user_info.nickname；下单时用户名快照，避免联表查询。` |
| **枚举字段** | `[业务含义]。枚举：VAL1=含义, VAL2=含义` | `订单状态。枚举：INIT=待支付, PAID=已支付, SHIPPED=已发货, COMPLETED=已完成, CANCELED=已取消。` |

### 6.3 冗余字段红线规则（强制）

1. **必须包含 `[冗余]` 前缀**（硬性关键词，便于 DBA 快速识别）；
2. **必须明确指出出处**：格式为 `来源：[表名.字段名]`；
3. **必须写明冗余目的**：是"避免高频 Join"、"历史快照"还是"汇总缓存"。
